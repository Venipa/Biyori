# HTML mockups and variants

When the ask is a mockup, a mock-up, a variant, variants, a visual option, options to compare, a preview before building, or "HTML only": make one local HTML file. Do not implement it in the app until they pick one.

Trigger words: mockup, mock-up, variant, variants, side by side, HTML only, preview the options, show options before coding.

- One self-contained `.html` file. All variants live in that file, stacked, labeled A, B, C. A short note under each label says what differs. Put one unchanged example next to the variant so the difference is visible.
- Inline `<style>` and, if a variant needs a click (open, close, toggle), a few lines of inline `<script>`. No modules, no fetch, no CDN, no Tailwind, no fonts, no image files.
- Icons are inline SVG. Do not generate images, screenshots, or mockup pictures. Do not use an image model for this.
- The file must open with `file://`. Do not start a server for it: no `python -m http.server`, `npx serve`, `live-server`, Vite preview, or `bun dev`. Do not open the running app as a stand-in.
- Write it outside the git repo, in the Cursor project folder, named `<topic>-mockup.html`. Do not put it under `apps/`, `public/`, or any path that would be committed.
- Show the preview in the chat when this client can render HTML in the conversation. If it cannot, open the browser at the `file://` URL of that file.
- Do not change product code, add a route, or add a dependency while the ask is only the mockup.
- Reply with the absolute path. Later tweaks edit that same file.
- A Cursor canvas is not a mockup. Use the HTML file.
- After the mockup is approved, implement it in the app.
